# 排查建议优化方案

**日期**: 2026-05-22
**状态**: 待审批

---

## 当前问题

单设备报告的"优化建议"区块存在三个问题：

### 1. key 不匹配

`_SUGGESTION_MAP` 使用旧 v2 的 rule_id（如 `base_cpu_info`、`ssh_or_adapi_authority`），但现在 `check_results` 的 key 是 CHECK_RULES 的 key（如 `CPU_CHECK`、`SSH_API_CHECK`）。大部分匹配失败，走了通用兜底。

### 2. 兜底文本太机器

```markdown
| 高 | SSH与API权限检测 | 检查项 SSH与API权限检测 状态为 fail，建议进一步排查 |
```

"建议进一步排查"对每个异常项都一样，没有提供任何有价值的行动指引。

### 3. 功能价值低

巡检报告已经有 ❌ 异常标记，重复一句"建议进一步排查"没有增量信息。用户需要的是**具体可操作的排查方向**。

---

## 方案

### A. 写死 67 条具体建议（推荐）

为每条 CHECK_RULES 写一条真正有用的排查建议。

原则：
- 能用"应/不应"句式描述预期的，直接给出操作指引
- 无法给出具体步骤的，至少指明排查方向
- 一句说完，不长篇大论

示例：

| 检查项 | 当前 | 改为 |
|--------|------|------|
| 电源状态检测 | 检查项 电源状态检测 状态为 fail，建议进一步排查 | 检测到电源模块异常，建议检查电源线连接，如为虚拟机请忽略 |
| SSH与API权限检测 | 检查项 SSH与API权限检测 状态为 fail，建议进一步排查 | 非管理员用户不应开启 SSH/API 权限，建议在用户管理中关闭不必要的远程访问权限 |
| 错误日志检测 | 检查项 错误日志检测 状态为 fail，建议进一步排查 | 设备存在错误日志记录，建议导出黑盒日志分析错误来源 |
| SSL策略检测 | 检查项 SSL策略检测 状态为 fail，建议进一步排查 | SSL 策略存在不安全算法或协议，建议在 SSL 策略配置中禁用 TLS 1.0/1.1 及弱加密套件 |
| 登录IP限制检测 | 检查项 登录IP限制检测 状态为 fail，建议进一步排查 | 未设置管理员登录 IP 限制，建议配置只允许信任 IP 段访问设备管理界面 |
| 默认开放端口检测 | 检查项 默认开放端口检测 状态为 fail，建议进一步排查 | 设备开放了非必要端口，建议在防火墙策略中关闭报表、智能DNS 等默认端口 |
| 硬盘检测 | 检查项 硬盘检测 状态为 fail，建议进一步排查 | 磁盘使用率异常或磁盘信息采集失败，建议检查磁盘分区空间 |
| 开启告警日志检测 | 检查项 开启告警日志检测 状态为 fail，建议进一步排查 | 邮件/snmptraps/syslog 告警均未开启，建议至少开启一项以便在设备异常时及时收到通知 |

对于无法给出具体建议的项，至少做到不同检查项有不同文案：

| 检查项 | 建议 |
|--------|------|
| 集群状态检测 | 集群状态异常，建议检查集群成员设备的网络连通性和同步配置 |
| 双机状态检测 | 主备状态异常，建议检查对端设备是否在线及心跳口配置 |
| 共享内存和信号量泄露检测 | 检测到共享内存或信号量异常，建议升级到 6.6R1 及以上正式版本 |

### B. 从 FIELD_RULES 自动生成

每个 `FIELD_RULES` 已有 `description`（"应/不应"句式），异常时自动反转：

- `description` = "电源模块应正常工作" → 异常时 = "电源模块工作异常，建议检查硬件"
- 但自动生成容易不自然，67 条量不大，写死更好

---

## 实施

1. 重写 `_SUGGESTION_MAP`：key 改为 CHECK_RULES key（`SSH_API_CHECK` 等），value 为具体排查建议
2. 区块标题从"优化建议"改为"排查建议"
3. 多设备模板同步更新
4. 覆盖率 67/67，不再有兜底文本

预估工作量：写 67 条建议文案，约 80 行代码。

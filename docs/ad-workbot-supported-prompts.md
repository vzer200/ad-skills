## 通用人工验收要求

- 每轮正式验收建议使用新的数字员工，并上传最新 AD skills 压缩包。
- 安装固定提示词：`请安装我刚上传的 AD skills 包，并确认 5 个 skill 都可用。`
- 所有需求必须有真实工具调用证据；不能只看最终文字回答。
- WorkBot 输出正文不要展示工具调用、命令、退出码、stdout/stderr 或脚本执行细节。
- WorkBot 侧 AD1/AD2 必须使用内网管理地址；人工文档中不记录任何密码。
- WorkBot 正在输出时不要切换页面；如页面空白，等待输出完成后刷新同一会话查看完整结果。

## 主线固定提示词

### R1 巡检

R1 使用交互式流程：第一句只表达“要巡检”，场景列表由 `check.py prompt --stage scene` 调用设备 GET `/sys/offline-check/` 获取。选择场景后必须先连接预检和查询历史；只有 `history` 的 `limit_reached=true` 时才进入强制确认，否则直接巡检。

| 编号 | 场景 | 固定交互 | 预期结果 |
| --- | --- | --- | --- |
| r1 | 单设备标准巡检 | `请对 AD1 做一次巡检。` -> `标准巡检` -> `limit_reached=true 时再发强制` | 输出单设备巡检报告，包含 `巡检结论 / 分类统计 / 设备基本信息 / 检查项明细 / 优化建议 / 健康评分`。 |
| r1-full | 单设备全量巡检 | `请对 AD1 做一次巡检。` -> `全量巡检` -> `limit_reached=true 时再发强制` | 同单设备模板，场景显示为全量巡检。 |
| r1-security | 单设备安全巡检 | `请对 AD1 做一次巡检。` -> `安全巡检` -> `limit_reached=true 时再发强制` | 同单设备模板，重点体现安全风险和建议。 |
| r1-all | 多设备标准巡检 | `请对 AD 所有设备做一次巡检。` -> `标准巡检` -> `任一设备 limit_reached=true 时再发强制` | 输出多设备摘要模板，包含 `巡检结论 / 设备概览 / 全局共性问题`。 |
| r1-all-full | 多设备全量巡检 | `请对 AD 所有设备做一次巡检。` -> `全量巡检` -> `任一设备 limit_reached=true 时再发强制` | 同多设备模板，避免展开所有设备长明细。 |
| r1-all-security | 多设备安全巡检 | `请对 AD 所有设备做一次巡检。` -> `安全巡检` -> `任一设备 limit_reached=true 时再发强制` | 同多设备模板，突出全局共性安全问题。 |

R1 人工检查重点：

- 第一轮只询问场景，不提前执行巡检或输出报告；场景选项不能写死，必须来自设备 `/sys/offline-check/`。
- 第二步选择场景后，应先查询历史/连接状态；历史上限必须按 `items` 归一化后的 `record_count/limit_reached` 判断，不能看 `total_items` 或 `total`。`items=[]` 时不能询问强制。
- 最终巡检应通过进度轮询完成，不能因为一次长任务触发平台超时；用户可见结果中要展示 `progress_text`，例如 `目前巡检 23/35`。
- 单设备检查项状态使用 `✅ 正常` 或 `❌ 异常`；检查项明细列名必须是 `检查项 / 具体说明 / 状态`，`具体说明` 用原生 `description` 或脚本内置说明，不允许出现 `当前发现` 列。
- 多设备只输出设备概览和全局共性问题，不输出 `巡检过程`、`原始报告`、脚本名或英文检查项名。

### R2 查询

R2 是当前状态/配置查询。默认规则：提示词带“配置”显示配置；带“状态/硬件/资源”显示状态；带“流量”显示流量；未明确维度时默认按配置处理。

| 编号 | 场景 | 主线固定提示词 | 预期结果 |
| --- | --- | --- | --- |
| r2 | 综合查询 | `帮我查一下 AD1 的配置、流量、设备状态和 SSL 证书到期时间。` | 输出配置、流量、设备状态和证书到期信息。 |
| r2-config | 单设备配置 | `帮我查一下 AD1 的配置。` | 只输出配置类信息。 |
| r2-config-all | 多设备配置 | `帮我查一下所有 AD 设备的配置。` | 查询所有 AD 设备配置，不混入状态指标。 |
| r2-vs | 单设备虚拟服务 | `帮我查一下 AD1 的虚拟服务配置。` | 只输出虚拟服务配置，不输出连接数、吞吐量等状态信息。 |
| r2-vs-all | 多设备虚拟服务 | `帮我查一下所有 AD 设备的虚拟服务配置。` | 查询所有 AD 设备虚拟服务配置。 |
| r2-node | 单设备节点 | `帮我查一下 AD1 的节点配置。` | 输出节点配置，工具命令必须使用 `overview.py node`。 |
| r2-pool | 单设备节点池 | `帮我查一下 AD1 的节点池配置。` | 输出节点池配置。 |
| r2-pool-all | 多设备节点池 | `帮我查一下所有 AD 设备的节点池配置。` | 查询所有 AD 设备节点池配置。 |
| r2-cert | 单设备证书 | `帮我查一下 AD1 的 SSL 证书到期时间。` | 输出证书名称、到期时间和风险提示。 |
| r2-cert-all | 多设备证书 | `帮我查一下所有 AD 设备的 SSL 证书到期时间。` | 查询所有 AD 设备证书到期信息。 |
| r2-traffic | 单设备流量 | `帮我查一下 AD1 的流量情况。` | 输出流量/连接相关状态。 |
| r2-traffic-all | 多设备流量 | `帮我查一下所有 AD 设备的流量情况。` | 查询所有 AD 设备流量。 |
| r2-status | 单设备状态 | `帮我查一下 AD1 的设备状态。` | 输出设备状态和资源使用信息。 |
| r2-status-all | 多设备状态 | `帮我查一下所有 AD 设备的设备状态。` | 查询所有 AD 设备状态。 |
| r2-hardware | 单设备硬件 | `帮我查一下 AD1 的硬件状态。` | 输出硬件/资源状态。 |
| r2-hardware-all | 多设备硬件 | `帮我查一下所有 AD 设备的硬件状态。` | 查询所有 AD 设备硬件状态。 |

R2 人工检查重点：

- 输出模板固定为 `查询结论 / 查询范围 / 查询结果`。
- 目标行使用 `目标设备：AD1（192.168.8.30）` 这类格式，不展示 URL scheme。
- 虚拟服务配置查询不能混入流量/状态字段；只有提示词提到状态、硬件、资源或流量时才显示对应指标。
- 输出不应出现英文模板残留、`覆盖说明` 或 R4 下发/回滚过程上下文。

### R3 感知分析

R3 是分析类能力，不替代 R2 的普通状态查询。主线只保留日志分析和指定虚拟服务流量趋势分析。

| 编号 | 场景 | 主线固定提示词 | 预期结果 |
| --- | --- | --- | --- |
| r3-traffic-vs | 指定 VS 流量趋势分析 | `对 AD2 设备的 test 虚拟服务进行流量趋势分析。` | 必须基于采集/数据库结果分析趋势，输出变化比例和证据，不使用“轻微/明显/严重”等主观风险列。 |
| r3-logs | 默认日志分析 | `对 AD2 设备的日志进行分析。` | 默认分析近 24 小时所有模块的告警和错误日志，按时间倒序最多展示最新 20 条。 |
| r3-logs-5d | 指定时间日志分析 | `对 AD2 设备近 5 天的日志进行分析。` | 按提示词时间范围分析所有模块的告警和错误日志，按时间倒序最多展示最新 20 条。 |

R3 人工检查重点：

- 输出模板固定为 `感知结论 / 分析结果 / 结论边界`。
- 流量趋势必须来自实际采集/数据库路径，不能凭模型描述。
- 日志分析必须覆盖告警和错误级别，默认不要带 `--modules`，确保 APPD、SYS 等模块的告警也会被输出；只有用户明确指定日志类型/模块时才加 `--modules`。当存在告警/错误或趋势变化时，结论不能写成“未发现明显异常”。

### R4 配置编排

R4 固定为两段流程：先生成 YAML，人工填写后上传；再由 WorkBot 解析 YAML、做现网预检，并让用户选择脚本模式或真实下发。主线覆盖提示词矩阵中的 VS、Pool/Node、HTTP Profile、HTTP Pre Rule 的创建、修改、删除和回滚；不是对设备 API 文档中所有 SLB 资源做全量覆盖。

#### R4 脚本模式主线

| 编号 | 场景 | 固定交互 | 预期结果 |
| --- | --- | --- | --- |
| r4-script | VS + 节点池 + 前置策略 + HTTP 优化 | `在 AD1 上帮我创建虚拟服务，引用节点池、前置策略和 http 优化策略。` -> 上传填写后的 YAML -> `我写完了 YAML。` -> `直接给出脚本。` | 生成 YAML、正向脚本、回滚脚本；做同名资源预检；不下发。 |
| r4-vs-pool-node-script | VS + 节点池 + 节点 | `在 AD1 上帮我创建虚拟服务，创建节点池并添加节点。` -> 上传填写后的 YAML -> `我写完了 YAML。` -> `直接给出脚本。` | 同上。 |
| r4-pool-profile-script | VS + 节点池 + HTTP 优化 | `在 AD1 上帮我创建一个 HTTP 虚拟服务，引用节点池和 http 优化策略。` -> 上传填写后的 YAML -> `我写完了 YAML。` -> `不需要下发。` | 同上。 |
| r4-pool-prerule-script | VS + 节点池 + 前置策略 | `在 AD1 上帮我创建虚拟服务，引用节点池和前置策略。` -> 上传填写后的 YAML -> `我写完了 YAML。` -> `先不下发。` | 同上。 |

#### R4 真实下发主线

| 编号 | 固定交互 | 预期结果 |
| --- | --- | --- |
| r4-delivery | `在 AD1 上帮我创建虚拟服务，引用节点池、前置策略和 http 优化策略。` -> 上传填写后的 YAML -> `我写完了 YAML。` -> `真实下发。` -> 人工检查后回复 `是。` | 下发前完成同名资源和引用资源预检；真实下发后外部验证资源存在；用户确认后回滚；回滚后外部验证资源不存在；最终保留三类产出物。 |
| r4-update-delivery | 创建同一套 SLB 配置 -> 上传修改说明字段的 YAML -> `我写完了 YAML。` -> `真实下发。` -> 外部验证更新后的 description -> `需要回滚。` -> 删除同一套 SLB 配置 | 覆盖 PATCH 修改链路、修改回滚链路和后续 DELETE 删除链路；修改/删除都必须走 plan/preflight/apply 和真实设备 API 验证。 |
| r4-delete-delivery | 创建同一套 SLB 配置 -> 上传删除 YAML -> `我写完了 YAML。` -> `真实下发。` | 覆盖 DELETE 删除链路；删除 YAML 必须包含回滚所需的 `rollback_method` 和 `rollback_path`；外部验证资源不存在。 |

R4 三个产出物必须同时出现：

| 产出物 | 用途 | 验收要求 |
| --- | --- | --- |
| `adops-bundle.yml` | 用户填写/留档的配置 YAML | Stage A 至少生成 YAML；上传完成后的每个 R4 关键回答都应列出该文件。 |
| `apply.py` | 正向下发脚本 | YAML 完成后必须作为用户可见产出物出现。 |
| `rollback_apply.py` | 回滚脚本 | YAML 完成后必须作为用户可见产出物出现，真实下发回滚后也要保留。 |

R4 人工检查重点：

- Stage A 第一条工具调用必须先清理上轮残留产物，再生成本轮 YAML；验收时应能看到 `init_env.py --confirm-clean` 出现在 YAML 渲染命令之前。
- Stage A 必须生成 YAML 产物并停止，不在聊天里追问大量字段。
- 用户填写 YAML 后，只回复 `我写完了 YAML。`，不额外解释配置内容。
- 下发或脚本生成前必须查询设备上的同名资源；同名资源存在时应复用并说明。
- 选择脚本模式时，不应下发到设备。
- 选择真实下发时，应先下发并让用户检查，再由用户确认回滚。
- 输出模板固定为 `配置结论 / 产出物 / 下一步`，不要展示长篇内部计划或内部 JSON 文件。
- 仅文字声称“已生成脚本”不算通过；必须看到 `adops-bundle.yml`、`apply.py`、`rollback_apply.py` 三个真实产出物。

## R2/R4 查询-新增-查询联动

该流程用于确认 R4 真实下发的资源能被 R2 查询到，并确认回滚后查询结果恢复。

| 阶段 | 固定交互 | 预期结果 |
| --- | --- | --- |
| 新增前准备 | `在 AD1 上帮我创建虚拟服务，引用节点池、前置策略和 http 优化策略。` -> 上传填写后的 YAML -> `我写完了 YAML。` -> `真实下发。` | R4 完成预检和真实下发，外部验证新增资源存在。 |
| 下发后查询 | `帮我查一下 AD1 的虚拟服务配置。` / `帮我查一下 AD1 的节点池配置。` / `帮我查一下 AD1 的配置。` / `帮我查一下 AD1 的流量情况。` / `帮我查一下 AD1 的设备状态。` / `帮我查一下 AD1 的 SSL 证书到期时间。` | R2 查询应使用查询流程，不重新触发配置流程；虚拟服务和节点池查询能看到新增资源。 |
| 回滚 | `是。` 或 `需要回滚。` | R4 执行回滚，外部验证新增资源不存在。 |
| 回滚后查询 | `帮我查一下 AD1 的虚拟服务配置。` / `帮我查一下 AD1 的节点池配置。` / `帮我查一下 AD1 的配置。` | R2 查询仍走查询流程，不夹带“回滚已生效”等配置流程话术；新增资源不应再出现。 |

## 扩展提示词

扩展提示词不属于主线稳定性 gate，主线全部通过后再单独验证。

### R2 扩展

| 编号 | 扩展提示词 | 预期结果 |
| --- | --- | --- |
| r2-short | `AD1 现在啥情况？` | 默认按配置查询，不展示状态/流量指标。 |
| r2-vs-alt | `看下 AD1 上有哪些 VS。` | 查询 AD1 虚拟服务配置。 |
| r2-vs-all-short | `所有 AD 的虚拟服务配置看下。` | 查询所有 AD 设备虚拟服务配置。 |
| r2-pool-node | `AD1 节点池和节点发我。` | 查询 AD1 节点池和节点配置。 |
| r2-cert-alt | `AD1 证书有没有快过期？` | 查询 AD1 证书到期情况。 |
| r2-resource-alt | `AD1 设备资源状态查一下。` | 查询 AD1 设备资源/硬件状态。 |

### R3 扩展

| 编号 | 扩展提示词 | 预期结果 |
| --- | --- | --- |
| r3-traffic | `对 AD1 设备的流量趋势进行分析。` | 对设备级流量趋势做分析。 |
| r3-conflict | `帮我分析一下 AD1 有没有地址冲突。` | 分析地址冲突，结论必须来自实际分析结果。 |
| r3-conflict-port | `AD1 有没有地址端口冲突？` | 分析地址/端口冲突，不能杜撰冲突。 |

### R4 扩展

| 编号 | 扩展提示词 | 预期结果 |
| --- | --- | --- |
| r4-vs-pool-script | `在 AD1 上帮我创建虚拟服务，挂节点池。` -> 上传 YAML -> `我写完了 YAML。` -> `直接给出脚本。` | 生成三类产出物，做预检，不下发。 |
| r4-audit-script | 上传 YAML -> `在 AD1 上检查这份 VS 配置会不会撞现网。` | 只做配置预检/碰撞检查，不下发；至少列出 YAML 产出物。 |

## 人工判定口径

- 主线：本文 `R1 巡检`、`R2 查询`、`R3 感知分析`、`R4 配置编排` 中标为主线的固定提示词。
- 扩展：本文 `扩展提示词` 中的提示词，主线稳定后再覆盖。
- 通过：提示词语义、工具调用证据、设备验证和用户可见模板均符合预期。
- 失败：无真实工具调用、工具调用与提示词语义不匹配、输出泄露工具/命令细节、模板不符合预期、R4 缺少三个产出物、真实设备状态与回答不一致，任一项出现都算失败。
